# Hosted acquisition: small follow-up, not implemented

The seam is absent and has a concrete consumer: `experiments/wave5/d14/lib/acquire.mjs` reports `unsupported-portable-acquisition`, while `fetch --local-artifacts ... --acquire-to ...` needs operator-provided copies. `server/paid-useful-jobs/lib/http.mjs` exposes result metadata from a process-local Map and no artifact route. H7's outbox receiver similarly imports an operator-provided bundle. This is useful delivery work for these existing consumers, not evidence of a paying external customer or validated demand.

Build only authenticated retrieval of two already-completed offline jobs: `lockfile-pin-delta` and `vendor-budget-impact`. Keep execution admission in the managed-order runtime, artifact identity in the mailbox/export representation, and notifications in the existing outbox. The interface in `hosted-acquisition.d.ts` and ten TODO cases are design scaffolding only. No service, new runtime, database migration, route, payment integration, or scheduler is installed by H21.

## Binding and retrieval

The execution admission path authenticates a stable principal ID, freezes the actual input bytes, and binds `(principalId, executionId, requestHash)` before any work. Persist the hash algorithm/version; reconcile the HTTP frozen-request hash and managed-order terms hash explicitly instead of assuming they are interchangeable. Existing raw Authorization-string equality is not an identity provider. Use the application's trusted authentication context; do not store bearer credentials or accept a principal field from the request body.

On completion, verify the existing execution.v1 envelope and receipt, then bind `jobId`, receipt hash, terms version, sample flag, and the exact named-output projection (`name`, `kind` default `file`, `bytes`, `sha256`). Top-level `executionId` is authoritative; do not require the optional nested receipt field. Copy the verified bytes into private service-owned immutable storage and commit metadata before returning an available retrieval record. Absolute `receipt.outputs[].path` is an implementation detail, never acquisition authority.

GET takes only the authenticated binding and exact promised artifact name/hash. It cannot call `runCreateOrder`, `runPaidOffer`, settlement, `deliverOnce`, enqueue, reconcile, or acknowledge. Missing, pending, expired, corrupt, ambiguous and restarted records cannot trigger execution or payment replay. A download does not mark `deliveredToBuyer`, buyer acceptance, `sold` or `usefulPaidWork`; `purchaseAuthority` stays false. Existing outbox notifications, if explicitly requested on completion, may reference the persisted identity but cannot extend expiry or authorize retrieval by themselves.

## Persistence, expiry and hostile paths

Use the existing managed-order file/Postgres ownership and reservation mechanisms. Add retrieval metadata and a private artifact area rather than a second job state machine. The current process-local HTTP cache can accelerate reads only after a durable lookup validates the binding. Never claim global exactly-once execution: an interrupted admission/completion record remains pending or ambiguous until explicit recovery. Store admission tombstones independently of result-byte retention; deleting artifacts must not free an execution ID for reuse. Capacity exhaustion refuses new admission rather than evicting those identities.

Persist server-generated UTC creation/expiry once (initial TTL 24 hours, bounded by deployment policy). Check server time on metadata and artifact reads and after opening bytes. GET cannot refresh TTL. Expiry removes access first, then a bounded janitor removes owned bytes; expired records retain minimal principal/request identity. Failure of cleanup cannot restore access. Restart, two competing writers, precommit and postcommit interruptions require real file-store and Postgres tests. Clock rollback/uncertain state fails closed; no request-supplied clock authorizes access.

Initial bounds: two promised output files, each at most the existing mailbox limit of 1,048,576 bytes and at most 2,097,152 bytes total; result metadata at most 64 KiB; 30-second request timeout; configurable bounded concurrent reads (start at four per process). Over-limit results are not silently truncated or promoted to available. Use a checked, bounded in-memory buffer before writing HTTP headers for this small scope. Reject Range initially with 416 and serve `application/octet-stream`, `nosniff`, attachment disposition, and `Cache-Control: private, no-store`. No public CDN or shared response cache.

Parse raw paths before URL normalization. Permit only the two catalog-promised basenames for the bound job, with a single canonical encoding; reject `..`, separators, NUL, absolute/drive/UNC paths, malformed or double encoding, query/fragment aliases and extra segments. The client supplies no directory or object-store URL. The store maps a validated opaque key to a service-owned directory that untrusted users cannot write. Open with no-follow, check all parent ownership/link boundaries, use the same file descriptor for fstat/read/hash, require regular file and link count one, and compare length/hash with the committed tuple before sending bytes. A `realpath` prefix check by itself is insufficient against a path-swap race. If the storage/backend cannot enforce these conditions, keep this seam disabled. Reject redirects; D14 checks origin and does not forward credentials cross-origin.
